# Step 4: database schema and integration

This records the Step 4 foundation. Step 5 now provides teacher-facing CRUD;
see [the current workflow and verification](crud.md). Remaining-scope statements
below describe the state at the Step 4 checkpoint.

## Requirements and provider choice

SQLite stores the teacher database locally. Drizzle ORM 0.45.3 defines the schema
and queries it through the Node-compatible libSQL client 0.18.0, using only local
`file:` URLs. No Turso account, cloud database, authentication token, or remote
database service is required. Drizzle Kit 0.31.11 generates versioned SQL
migrations from the JavaScript schema; production does not need Drizzle Kit.

The brief allows a suitable database tool/ORM, with Prisma as an example rather
than a requirement. Drizzle fits the inherited JavaScript application without
adding a TypeScript conversion or adopting a release-candidate generator.
SQLite suits the current single-app classroom deployment. It is not a design
for multiple independently scaled server replicas sharing one database file;
consider a client/server database such as PostgreSQL if that becomes necessary.

References: [Drizzle's libSQL integration](https://orm.drizzle.team/docs/sqlite/connect-turso),
[schema declarations](https://orm.drizzle.team/docs/sql-schema-declaration), and
[versioned migrations](https://orm.drizzle.team/docs/migrations). This project
pins the stable 0.x ORM/tool versions rather than the documentation's newer RC.

| Requirement | Implementation |
| --- | --- |
| 4.1 Lists, words, and each word's phonemes | `word_lists`, ordered `words`, and ordered `word_phonemes`; transactional ORM writes are verified. Teacher-facing CRUD follows in Step 5. |
| 4.2 Multi-character phonemes | A token is a `TEXT` symbol referencing `phonemes`; a position identifies the whole token, never a character within it. |
| 4.3 Activity/settings/metadata | Configurations store type, difficulty/grid size or answer/guess count, hints toggle, output theme/filename, title, and timestamps. Words have optional English text and hint metadata; inventory rows retain phoneme examples/labels. |
| 4.4 Multiple configurations | One list can support several independent configurations, each with a stable ID; ORM readers reconstruct their ordered content. |
| 4.5 Database tool/ORM | Drizzle schema, generated SQL/snapshot/journal, migration runner, SQLite driver, and server-only Next.js connection. |

## Relationships

```text
word_lists ───< words ───< word_phonemes >─── phonemes
     │            │
     └───< activity_configurations
                  └── Wordle answer references a word in the same list
```

The schema is `src/lib/db/schema.mjs`. The initial migration and Drizzle's
schema snapshot/journal are tracked under `drizzle/`.

- Lists own their words; words are ordered by `position` and identified by UUIDs
  generated by the ORM. Identical text/tokens can appear as separate word records.
- The application's word limit is 1–15 complete phoneme tokens, matching the
  generation boundary; Step 5's write service must apply that limit. The table
  permits positions 0–14; its primary key prevents duplicate positions.
  Reconstruction explicitly sorts both word and token positions. Repeated
  phonemes such as `['p', 'p', 'æɪ']` remain separate tokens.
- Configurations belong to one list. Wordle selects one answer word; a composite
  foreign key ensures that answer belongs to its list. Word Search uses the
  ordered list rather than a fixed example.
- Type-specific CHECK constraints allow Wordle guess counts 3–8 with an answer,
  or Word Search sizes 6–15 with easy/hard difficulty. Irrelevant settings must
  be null. Configuration records cannot mix the two settings shapes.
- Database checks constrain metadata lengths, theme, boolean hints, nonnegative
  integer positions, and safe HTML filenames. Foreign keys reject unknown
  inventory tokens and orphaned relationships.
- Deleting a list cascades to its configurations, words, and token rows. Deleting
  an individual selected Wordle answer is blocked until its configuration is
  changed/deleted; Step 5 must explain that conflict to the teacher. Inventory
  symbols referenced by words cannot be deleted.
- `createdAt` and `updatedAt` use UTC ISO timestamps. Drizzle updates `updatedAt`
  on ORM updates; direct administrative SQL must maintain that field itself.

SQLite cannot enforce every cross-row application rule here: nonempty/contiguous
token arrays, maximum list size, and words fitting a selected grid must be
validated by the write/generation services as those workflows are connected in
Steps 5–7. This schema step does not mark the final validation audit complete.

## Connection, migration, and startup

`src/lib/db/connection.mjs` opens a local file, enables foreign keys, a five-second
busy timeout, and write-ahead logging (WAL). One connection keeps connection-local
settings consistent. `src/lib/server/database.js` is guarded by `server-only`
and shares a connection across route requests/development reloads. The database
path is runtime configuration; an explicit tracing annotation keeps teacher
files outside Next.js build output.

Local production startup resolves the path to an absolute value before migration
and server boot. This matters because Next.js' generated standalone server changes
its working directory: both processes must still open the same database file.
The local HTTP test deliberately supplies a relative path to verify that behavior.

By default, local storage is `data/phonemele.db` relative to the project. Set
`DATABASE_PATH` to choose another server-side file path. It is not a browser
environment variable. The local `data/` directory is excluded from Git and the
Docker build context; database files are not assessment source code.

```sh
npm ci
npm run db:migrate
npm run dev
```

`npm run dev` runs the migration first automatically. `npm run start` also applies
migrations before starting the standalone server; run `npm run build` first.
Startup adds only the 43 reference phonemes, not sample teacher lists. Repeating
migration/startup preserves existing words and configurations. A migration error
stops startup instead of silently serving against an incompatible schema.

For future schema changes:

```sh
npm run db:generate -- --name=describe_the_change
npm run db:migrate
```

Review and commit generated SQL and snapshots. Do not rewrite migrations already
applied to teacher databases. Back up data before applying later migrations.

`/health` remains application liveness. The new `/health/database` checks database
access and the seeded inventory, returning `200` with
`{"status":"ok","database":"sqlite"}` or a generic `503` setup message. Detailed
failures stay in server logs. Both health endpoints use `Cache-Control: no-store`.

## Docker persistence

The image copies the ORM runtime, database modules, reference inventory, and
tracked migrations. It never copies the host database or the fixture writer.
Its non-root startup process migrates `/app/data/phonemele.db` before accepting
requests. The container health check now uses `/health/database`.

Compose mounts the named `teacher-data` volume at `/app/data` (normally
`assignment2_teacher-data`). The image prepares this directory for the `node`
user; a fresh Docker-managed volume inherits the directory's ownership.

Use the build/start commands in `docker.md`, including this machine's optional
trusted-CA override. The prebuilt image can be started with:

```sh
docker compose up --no-build -d --wait
```

`docker compose down` stops/removes the app but preserves the teacher volume.
Do not add `--volumes`/`-v` or prune volumes containing teacher data. Local and
Docker storage are separate; starting Docker does not import the local file.
Back up a stopped volume, or use SQLite's backup facility; copying only a live
`.db` file can omit changes in its WAL sidecar.

## Verification

```sh
npm run lint
npm run build
npm run test:database
npm run test:backend
npm run test:docker
```

Database tests use a fresh temporary directory, never the default teacher file.
They migrate an empty database, run 18 storage/constraint checks, restart in a
separate process, reapply migrations, and run four persistence/read checks.
The fixture writer refuses an existing database containing teacher lists.

Backend tests start a standalone server with their own temporary database. The
28 normal HTTP checks include both builders, browser assets, generation, existing
validation, and database readiness. An additional local-only failure check makes
that temporary inventory incomplete and confirms readiness 503 while liveness
remains 200. No external/test-target database is changed by that failure check.

Docker tests create a uniquely named, labelled verification volume, migrate it
on startup, run 28 HTTP checks and the 18 storage checks, then remove/recreate
the container on the same volume. Four reads verify persisted data before the
28 HTTP checks run again. Test code is injected into the temporary container,
not shipped in the production image. Cleanup removes only the owned container
and labelled test volume, leaving any teacher volumes alone.

Verified on 7 October 2026: local lint/build, all 22 database checks, all 29 local
HTTP checks, and Docker build/health/non-root runtime/container-recreation
persistence passed. The final commit also verifies that the image has no host
database and no fixture writer. Only owned fixture data is removed during tests.

The package explicitly declares ES modules so command-line migrations can reuse
the existing JavaScript phoneme inventory without ambiguous module detection.
Next.js emits a matching ES-module standalone server; no TypeScript conversion
or generated TypeScript client is introduced.
